# Runtime incidents and desktop notifications

The Electron host observes saved flow deployments every five seconds, independently of whether Deploy is open. It records transitions for failed/interrupted/stalled runtime, uncertain orders, unverified close, and an existing native-protection record needing attention. It does not infer absent protection capability, identify connection loss or position mismatch separately from generic runtime failure, or change trading behavior.

Deploy shows the latest ten incident events for the selected bot, including desktop delivery status. The local file beside exchange-connections.json retains the latest 200 events across bots, plus condition fingerprints for deduplication. Missing deployments are not evidence of recovery. A pending close retry retains an existing close incident until verified closed. Observing a replacement deployment suppresses queued notifications for its predecessor without synthesizing recovery. Clearing means that specific condition is no longer observed; it is not an account-safety claim. Transient conditions shorter than the sampling interval may be missed; the execution audit journal remains the detailed record.

Detection and recovery notifications use fixed generic text. No bot name, account, market, raw runtime error, or destination error enters the OS message. The local incident record contains identifiers, fixed reason codes, timestamps and delivery metadata only. It does not copy account credentials or error strings.

Transitions are persisted atomically before delivery. A global 30-second delivery interval limits bursts across bots. A failed destination receives at most three attempts per event, with the retry budget persisted before each attempt. Delivery observes native `show`/`failed` events and times out after five seconds. `Shown` means the OS reported showing it, not that a person read it. A process crash after showing but before recording success can cause a bounded duplicate; exactly-once notification delivery is not promised. Superseded pending events are not delivered. An exhausted or superseded event is shown as unavailable.

If incident storage fails, the runtime continues; Deploy shows a monitoring warning and no new undurable notification is sent. A corrupt history file disables the observer until the storage issue is repaired and the host restarted. The monitor never retries trading orders, resumes a bot, or contacts an external notification destination.

Native notification support depends on the OS, permissions and app packaging. In particular, macOS requires a signed Electron application; unsigned development builds can emit failure instead of displaying a message. See [Electron notifications](https://www.electronjs.org/docs/latest/tutorial/notifications). In-app history remains available even when desktop delivery fails. Browser-only preview without the Electron host does not provide native notifications.

This is partial issue #15. Opt-in external delivery, independent backend-down detection, source-data freshness, per-cause connection/position diagnostics and live destination acceptance remain follow-up work. An observer inside the backend cannot notify while that entire process is down.
